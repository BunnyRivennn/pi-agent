# NL2SQL 数据合成配额与管道方案（5013 表全库版）

> 本文档是 `NL2SQL 训练数据分析与合成方案.md` 的收口版本，专门解决一个问题：
> 原方案的样本配比是按"一个数据库"写的，现在面对 5013 张表，各难度、各查询类型到底该合成多少条。
> 本文档确定的数字可直接作为合成管道的配额配置，后续工程实现以本文档为准。

---

## 一、先纠正一个前提：不是 5000 个数据库

扫描 `train.db` 的实际结果：

| 指标 | 实际值 |
| --- | ---: |
| SQLite 文件数 | 1（`train.db`） |
| 表数量 | 5,013 |
| 单表行数 中位数 | 26 |
| 单表行数 上限 | 100 |
| 单表字段数 中位数 | 9 |
| 原始训练数据 | 41,522 条，覆盖全部 5,013 张表 |
| 原始数据 每表样本数 中位数 | 6 条（最多 51 条） |

这是 TableQA 式的"一表一库"数据集：每个 `table_id` 对应一张宽表，表之间没有外键关系，所以**单表查询约束不是人为限制，而是数据本身决定的**，这一点与原方案一致。

由此得到两个关键推论：

1. **不能用"单库配额 × 5013"做换算。** 原方案 30,000 条的配比如果按表乘，会得到 1.5 亿条这种无意义的数字。正确做法是**总量固定，按表的能力把配额摊下去**。
2. **真正的瓶颈是行数，不是表数量。** 全库每张表最多 100 行，中位数只有 26 行。这直接限制了 `GROUP BY` 的分组数、`HAVING` 的过滤空间和 `LIMIT` 的取值范围——复杂 SQL 的合成上限由此决定，而不是由表数量决定。

### 1.1 单表约束（硬性，全程不变）

**本方案所有样本均为单表查询，不生成任何多表关联。** 这不是阶段性取舍，而是数据结构决定的结论：

| 核查项 | 结果 |
| --- | ---: |
| 定义了外键的表 | **0 / 5,013** |
| 表间可信关联关系 | 无 |
| 每张表的业务独立性 | 每个 `table_id` 是一张独立宽表，有自己的业务主题 |

因此管道须强制执行：

1. 每条 SQL 的 `FROM` 只允许出现一张表，且必须是本次任务指定的目标表。
2. 禁止 `JOIN`（含 `INNER` / `LEFT` / `RIGHT` / `FULL` / `CROSS` / 逗号隐式连接）。
3. 禁止 `UNION` / `UNION ALL` / `INTERSECT` / `EXCEPT` 等跨查询集合操作。
4. 第六节 Hard 中的"子查询"任务，**子查询也只能引用同一张目标表**（如用于聚合结果比较的自关联子查询），不得引用其他表。
5. 静态校验阶段解析 SQL 的 AST，提取表引用集合，`len(set) != 1` 直接判失败，不进入执行验证。

### 1.2 一个必须避开的陷阱：`possible_join_columns`

`database_inspection.json` 顶层有一个 `possible_join_columns` 字段，列出 22 组"可能可以关联"的列。**这个字段不可用，必须忽略。**

它的生成逻辑是按"字段名相同"把表归组，而全库 5013 张表的字段统一命名为 `col_1`、`col_2`……所以几乎每张表都会被归进 `col_1` 这一组。**字段同名在这里完全不代表语义相同**——某张表的 `col_1` 是省份，另一张表的 `col_1` 可能是产品编号。

照这个字段做关联会产出大量语义荒谬但能执行成功的 SQL，而执行验证发现不了。管道预处理时不要读取该字段。

## 二、全库表能力画像（配额的分母）

### 2.1 一个好消息：字段业务含义 100% 可用

原方案担心字段是 `col_1`、`col_2` 这类匿名名、业务含义要靠猜。实测结论相反：

| 核查项 | 结果 |
| --- | ---: |
| `train.tables.json` 中有表头的表 | 5,013 / 5,013 |
| 表头列数与数据库列数完全一致的表 | **5,013 / 5,013（100%）** |

`train.tables.json` 每行给出 `name`（即 `Table_xxx`）、`header`（业务列名，按列顺序对齐 `col_1..col_N`）、`title`（表格标题）、`types`。**列数全库零偏差，所以 `col_N` → 业务名的映射是可靠的，不需要启发式推断。**

这改变了两件事：

1. 原方案 8.7.3.1 的"映射不明确则降级使用"条款，实际几乎不会触发，`semantic_known` 不是瓶颈。
2. **聚合能力判定必须用业务名，不能用字段类型。** 一个 REAL 列叫"序号"不能 SUM，叫"同比(%)"不能 SUM 但可以 AVG，叫"土地出让金(亿元)"才可以 SUM。这是本方案列能力判定的核心依据。

### 2.2 列能力判定规则

| 能力 | 判定规则 |
| --- | --- |
| `numeric`（可筛选/比较/排序） | 数值列，distinct ≥ 3，max ≠ min，非空率 ≥ 50% |
| `aggregatable`（可 MIN/MAX/AVG） | 在 `numeric` 基础上，业务名**不**命中编号类正则（序号/编号/代码/排名/年份/月份/日期/电话/邮编…） |
| `summable`（可 SUM） | 在 `aggregatable` 基础上，业务名命中可加总类（金额/收入/产量/数量/人数/面积/总额/出让金…）且**不**命中比率类（率/占比/同比/均价/评分/指数…） |
| `groupable`（可 GROUP BY） | TEXT 列，2 ≤ distinct < 行数 且 distinct ≤ min(30, 行数×0.6) |
| `having_friendly`（可 HAVING） | 在 `groupable` 基础上，3 ≤ distinct ≤ 15 且 平均组内行数 ≥ 3 |
| `date`（时间列） | 仅认两类：① 纯年份数值列（1900~2100 整数，按数值比较）② 样例值 80% 以上匹配可比较日期格式 |

> 比率类禁止 SUM 这条很实际：库里大量列是"同比""环比""溢价率""去化周期环比"，加总完全无意义，但类型是 REAL，不设规则必然被错误聚合。

### 2.3 全库能力实测结果

脚本 `build_table_pools.py` 扫描 5,013 张表的结果：

| 能力维度 | 可用表数 | 占比 |
| --- | ---: | ---: |
| 行数 ≥ 20 | 2,912 | 58.1% |
| 行数 ≥ 50 | 1,668 | 33.3% |
| 有数值列（可筛选/排序） | 4,267 | 85.1% |
| 有可聚合列（可 MIN/MAX/AVG） | 2,428 | 48.4% |
| **有可 SUM 列** | **944** | **18.8%** |
| 有 HAVING 友好分组列 | 2,192 | 43.7% |
| 有可文本匹配列（LIKE/IN/DISTINCT） | 4,963 | 99.0% |
| **有可靠时间列** | **430** | **8.6%** |

**两个真正的瓶颈，都不是表数量：**

1. **可 SUM 列只有 944 张表（18.8%）。** 严格按业务名判定后，大部分数值列是比率、编号或指标名含时间词的派生值。所以合成时聚合指标要以 `COUNT` / `AVG` / `MAX` / `MIN` 为主，`SUM` 只能用在这 944 张表上，不能当成通用手段。
2. **可靠时间列只有 430 张表（8.6%）。** 库内日期格式极脏——`2006.8`、`18/10/31`、`1976年1月20日`、`--`、REAL 存的 `2018.0` 混在一起；而表头含"时间/年度/月份"的 1,889 列里很多是"上一年度同期成交""4月份去化周期环比"这种指标名，并不是日期列。所以**时间类任务的配额上限约 1,150 条，原方案规划的 2,100 条放不下**，已在第六节下调。

此外，`YYYY/M/D`、`YYYY-M-D` 这种月日不零填充的格式，字符串比较会把 `2016/9/1` 排到 `2016/10/1` 之后。这类列标记为 `range_safe = false`，**只允许等值和 LIKE 前缀匹配，禁止 BETWEEN 范围查询**。

## 三、配额换算逻辑

放弃"每表生成 N 条"，改用三层约束同时成立：

```
总量目标（固定）
      ↓  按难度拆
难度配额（Easy / Medium / Hard）
      ↓  按任务拆
任务配额（10 类查询任务）
      ↓  映射到能力池
表池（P0 ~ P5，每个任务只能在匹配的池里取表）
      ↓  除以池内表数
每表密度（必须 ≤ 密度上限，否则扩池或降配额）
```

**密度上限规则：** 同一张表同一任务类型最多 2 条，同一张表合计最多 8 条。原始数据每表中位数 6 条，合成数据保持同量级，避免某几张表被过度采样。

### 4.1 为什么要把 P1 拆成 P1 / P1A

这是定池过程中最关键的一次修正。初版把"有可聚合数值列"作为分组类池的准入条件，算出 P2 只有 686 张表，配额根本摊不开。

原因是搞错了一件事：**`COUNT(*)` 对任何表都成立。** 一张有分组列但没有可聚合数值列的表，照样能做 `GROUP BY 省份 COUNT(*)` 和 `HAVING COUNT(*) > 3`。只有需要 `SUM` / `AVG` / `MIN` / `MAX` 真实数值指标时才必须有可聚合列。

拆开之后：

- **P1 / P2 / P3** 不要求可聚合列 → 表数分别 2,452 / 2,150 / 1,477，配额摊得开。
- **P1A / P4** 要求可聚合列 → 1,176 / 571，专供需要数值指标的任务。

同理，`P3`（HAVING）只要求 HAVING 友好分组列，用 `HAVING COUNT(*) > n` 就能成立；`P4` 才额外要求可聚合列，因为"多聚合指标"至少要有一个数值指标配合 `COUNT`。

### 4.2 稀缺池

**P4（571）、P5（299）、P5L（368）是稀缺池**，配额分配时必须先处理。分配器按池大小升序遍历任务，就是为了让稀缺池先占位——否则这些表会被宽松池的任务先占满（实测过，设单表上限 8 时就发生了，详见 6.5 节）。

## 五、总量目标与分阶段节奏

原文档中出现过 1,000 / 2,500 / 30,000 三个数字，实际是三个不同阶段的目标。本文档统一为：

| 阶段 | 目标产出（通过全部校验） | 目的 | 准入条件 |
| --- | ---: | --- | --- |
| **阶段一 冒烟** | 1,000 条 | 验证管道链路、字段语义判断、校验器有效性 | 无 |
| **阶段二 中试** | 5,000 条 | 验证各 SQL 结构的生成成功率与模板多样性 | 阶段一执行通过率 ≥ 90%，语义抽检准确率 ≥ 85% |
| **阶段三 扩量** | 30,000 条（含前两阶段） | 构建完整 SFT 数据池 | 阶段二各结构成功率 ≥ 80%，模板重复率 ≤ 15% |

**生成量要留冗余。** 按阶段一实测通过率反推，目标 30,000 条合格样本需要生成 38,000 ~ 45,000 条候选（预估综合通过率 70% ~ 80%）。管道按"目标数 ÷ 实时通过率"动态补生成，不是一次性生成 30,000 条就结束。

### 6.5 单表上限为什么是 10 而不是 8

初版设"同表合计 ≤ 8"，运行后有两个任务配不满：`多条件 AND/OR` 缺 660 条、`复杂 AND/OR 嵌套` 缺 268 条，总量只到 29,072。

原因不是 P1 池不够大（2,452 张表），而是**P1 里那些同时属于 P2 / P3 / P4 的表，已经被稀缺池任务先占满了 8 条额度**。分配器按池大小升序处理，P1 任务排在最后，轮到它时只剩 547 张表可用。

放宽到 10 后 30,000 条全部配满，且**实测单表最大值就是 10——设成 12 也不会更高**，说明 10 是这套配额的自然上限。

最终密度：

| 指标 | 值 |
| --- | ---: |
| 覆盖表数 | 4,987 / 5,013（99.5%） |
| 单表最多 | 10 条 |
| 覆盖表均摊 | 6.02 条 |
| 同表同任务超限 | 0 处 |
| 同表合计超限 | 0 处 |

均摊 6.02 条与原始数据每表中位数 6 条、最多 51 条属同一量级，密度合理。

### 6.6 配额与结构标签的关系

配额是**样本名额**，不是结构出现次数。一条 SQL 可以同时带 `where` / `group_by` / `order_by` / `limit` 四个结构标签，但只占用一个名额。

因此按上表执行后，各结构的**实际出现次数**会远高于对应任务的配额。例如 `WHERE` 的预估覆盖率在 70% 以上，`GROUP BY` 在 8,000 条以上。结构覆盖率要单独统计，不能用配额表反推。

### 6.7 从哪些表生成：工单文件 `synthesis_tasks.jsonl`

配额表只回答"每类任务多少条"。"**具体用哪张表生成哪条**"这个问题，答案不在文档里，而在落盘的工单文件里——28,051 行，每行一个 `(表, 任务)` 二元组，已经把 30,000 条配额全部派到具体表上。

工单行格式：

```json
{"table_name":"Table_a7c1bdfd3b0611e9bee0f40f24344a08","difficulty":"hard","task":"groupby_multiagg_having","task_name_cn":"GROUP BY + 多聚合 + HAVING","pool":"P4","target_count":2}
```

| 字段 | 含义 |
| --- | --- |
| `table_name` | 目标表名，直接用于 `FROM` |
| `difficulty` | easy / medium / hard，写入样本标签 |
| `task` | 任务英文键，对应第六节配额表一行 |
| `task_name_cn` | 中文任务名，拼 prompt 时用 |
| `pool` | 该表入选的表池，便于回溯 |
| `target_count` | 这张表在这个任务下要生成几条（1 或 2） |

合成管道的主循环就是遍历这个文件：

```python
for line in open("synthesis_tasks.jsonl", encoding="utf-8"):
    job = json.loads(line)
    profile = pools_index[job["table_name"]]      # 来自 table_pools.json
    prompt  = build_prompt(profile, job)          # 注入表头 + 列能力 + 任务要求
    samples = llm_generate(prompt, n=job["target_count"])
    validate_and_save(samples, job)               # 静态校验 → 执行验证 → 入库
```

关键点：**prompt 里不要让模型自己挑表、挑列、挑难度。** 表由工单指定，可用列由 `table_pools.json` 的能力画像指定（`groupable_columns` 给 GROUP BY、`summable_columns` 给 SUM、`range_safe_date_columns` 给 BETWEEN），任务由 `task` 指定。模型只负责在给定约束内写 SQL 和问题。这是把执行通过率做上去的前提。

一个真实工单示例——`Table_a7c1bdfd3b0611e9bee0f40f24344a08`（46 行；可聚合列"奖金（万元）"；HAVING 友好分组列"奖项"、"等级"各 4 个取值、平均组内 11.5 行）被分到 10 条，跨 8 个任务：

| 难度 | 任务 | 表池 | 条数 |
| --- | --- | --- | ---: |
| medium | 时间条件 + 聚合 / 分组 | P5 | 2 |
| hard | 时间 + 聚合 + 分组 + 排序 | P5 | 2 |
| hard | GROUP BY + 多聚合 + HAVING | P4 | 1 |
| hard | W+G+H+O+L 五子句组合 | P4 | 1 |
| medium | 聚合函数（多指标、带 WHERE） | P1A | 1 |
| medium | GROUP BY + 聚合 | P2 | 1 |
| easy | 简单聚合 COUNT/SUM/AVG/MIN/MAX | P1A | 1 |
| easy | 简单时间条件 | P5L | 1 |

这张表同时进了 P5（可靠时间列，只有 299 张表）和 P4（571 张表），两个最稀缺的池都占，所以难任务优先落在它身上，10 条额度里 4 条是时间类、2 条是 Hard 分组类；同时它也承担 2 条 Easy 样本，保证同一张表上有难度梯度，后面做课程式训练时可以按表对齐。

反过来说，只进了 P0 / P6 这两个宽松池的表（行数少、无可靠数值列和时间列），每张通常只分到 1 条基础 WHERE 或 LIKE 样本——这是 6.5 节里"覆盖表均摊 6.02 条但单表最多 10 条"这个落差的来源。

> 要调整配额，改 `allocate_quota.py` 里的 `QUOTA` 列表重跑即可，不要手改 jsonl。

## 七、阶段一、阶段二的配额怎么取

阶段一（1,000 条）和阶段二（5,000 条）**不按 30,000 的比例等比缩小**。前期目的是暴露问题，所以要让稀缺结构先过一遍。

### 7.1 阶段一 冒烟 1,000 条

| 难度 | 配额 | 说明 |
| --- | ---: | --- |
| Easy | 300 | 只验证链路，不需要多 |
| Medium | 400 | 覆盖 GROUP BY、HAVING、排序 |
| Hard | 300 | **故意超配**，优先暴露复杂结构的失败模式 |

任务层面要求：第六节的 28 个任务每个至少生成 20 条，`GROUP BY + HAVING`、`5 子句组合`、`时间 + 聚合 + 分组 + 排序`这三类各至少 50 条。

**表只从 P4（571 张）和 P5（299 张）这两个稀缺池里选**，因为这两个池的表最容易出问题——HAVING 阈值反推、日期格式、分组数不足都集中在这里。做法是从 `synthesis_tasks.jsonl` 里过滤 `pool in ("P4", "P5")` 的工单先跑，这部分工单约 2,500 行，足够切出 1,000 条冒烟样本。

### 7.2 阶段二 中试 5,000 条

按 30,000 配额表的比例等比取 1/6，但做两处调整：

- 阶段一中失败率 > 30% 的任务，配额**减半**，先修 prompt 和校验规则，不靠堆量解决。
- 阶段一中模板重复率 > 25% 的任务，强制扩大表池或增加字段轮换约束后再生成。

## 八、行数上限带来的硬约束

全库单表最多 100 行、中位数 26 行，这对合成 SQL 有几条不可绕过的限制。**管道必须在 SQL 生成前就把这些约束写进 prompt，而不是等执行后再过滤。**

| 约束 | 原因 | 管道做法 |
| --- | --- | --- |
| `LIMIT` 取值只能在 1 ~ 10 | 表最多 100 行，`LIMIT 50` 等于没过滤 | 按 `min(10, 行数 // 5)` 动态给上界 |
| `GROUP BY` 分组列的 distinct 必须 ≤ 15 | 否则每组只有 1 ~ 2 行，聚合无意义 | 选表时用 P3 / P4 池的判定条件 |
| `HAVING` 阈值必须从真实聚合结果反推 | 随手写 `HAVING COUNT(*) > 10` 在 26 行的表上必返回空 | **先执行不带 HAVING 的分组查询，拿到真实分布，再取中位数附近的值作为阈值** |
| 禁止对 distinct = 行数 的列做 `GROUP BY` | 这类列是主键或编号，分组后每组一行 | 选列阶段过滤 |
| 空结果样本要限额 | 空结果 SQL 无法验证语义是否正确 | 空结果样本占比 ≤ 3%，且只允许出现在 Hard 的"边界场景"任务中 |
| 日期列要先确认格式 | 926 张表有日期型列，但格式混杂（`2018-01-01`、`20180101`、`2018年1月`） | 按格式归类后，只对 SQLite 可直接比较的格式生成时间范围查询 |

**`HAVING` 阈值反推是整个管道最容易出错的环节。** 不做这一步，带 `HAVING` 的四类任务（`GROUP BY + HAVING` 1,200、`GROUP BY + 多聚合 + HAVING` 1,100、`GROUP BY + HAVING + ORDER BY` 900、5 子句组合 1,000，**合计 4,200 条**）会大面积返回空结果。

### 9.1 表画像结构

`table_pools.json` 的实际结构：

```json
{
  "pools": { "P0": ["Table_xxx", ...], "P1": [...], "P1A": [...], "P2": [...],
             "P3": [...], "P4": [...], "P5": [...], "P5L": [...], "P6": [...], "PMG": [...] },
  "table_profiles": {
    "Table_xxx": {
      "row_count": 46,
      "column_count": 6,
      "title": "2019年某评奖结果",
      "numeric_columns":      [{"name": "col_3", "business_name": "奖金（万元）", "distinct": 12, "min": 1.0, "max": 50.0}],
      "aggregatable_columns": [{"name": "col_3", "business_name": "奖金（万元）"}],
      "summable_columns":     [{"name": "col_3", "business_name": "奖金（万元）"}],
      "groupable_columns":    [{"name": "col_2", "business_name": "奖项", "distinct": 4,
                                "avg_group_size": 11.5, "having_friendly": true}],
      "having_friendly_columns": ["col_2", "col_4"],
      "date_columns":            [{"name": "col_5", "format": "YYYY-MM-DD", "range_safe": true}],
      "comparable_date_columns": ["col_5"],
      "range_safe_date_columns": ["col_5"],
      "text_columns":  ["col_1", "col_2", "col_4"],
      "semantic_known": true,
      "pools": ["P0", "P1", "P1A", "P2", "P3", "P4", "PMG", "P6"]
    }
  }
}
```

字段用途：

- `summable_columns` 是唯一允许写 `SUM` 的列；`aggregatable_columns` 可用 `MIN/MAX/AVG/COUNT`；`numeric_columns` 只保证可做数值筛选和排序
- `groupable_columns[].having_friendly` 为 true 才允许生成 `HAVING`（分组数 ≤15 且平均组内行数够）
- `range_safe_date_columns` 是唯一允许写日期 `BETWEEN` / `>` 的列；`comparable_date_columns` 但不 range_safe 的只允许等值和 `LIKE` 前缀匹配
- `semantic_known` 实测 5,013/5,013 全为 true（见 2.1 节），但保留该字段，为 false 时只允许参与 COUNT 和基础筛选

### 9.2 分配算法（`allocate_quota.py` 实现）

```python
PER_TASK_CAP  = 2    # 同表同任务上限
PER_TABLE_CAP = 10   # 同表合计上限（见 6.5 节为何是 10）

# 关键: 按池大小升序处理任务, 让稀缺池先占位
ordered = sorted(QUOTA, key=lambda q: len(pools.get(q[3], [])))

for difficulty, task, name_cn, pool, quota in ordered:
    avail = [t for t in pools[pool] if TASK_REQUIRE.get(task, lambda p: True)(profiles[t])]
    got = 0
    while got < quota:
        # 轮内按已用总数升序, 冷门表先拿, 保证覆盖均匀
        avail.sort(key=lambda t: (used_total[t], t))
        picked = False
        for t in avail:
            if used_task[(t, task)] >= PER_TASK_CAP: continue
            if used_total[t]       >= PER_TABLE_CAP: continue
            assign(t, task); got += 1; picked = True
            if got >= quota: break
        if not picked:
            report_shortfall(task, quota - got); break   # 不降质量硬凑
```

两处排序是这个算法能零违例配满的原因：

1. **任务顺序按池大小升序** —— P5（143 表）、P4（571 表）这类稀缺池先选表，否则它们要的表早被 P0/P6 的大额任务占满
2. **轮内按已用数升序** —— 每发一条就重排，样本自然摊到冷门表上，避免前几百张表吃掉全部额度

`TASK_REQUIRE` 是任务级精筛，在池的基础上再加硬条件，共 12 条。例如：

```python
"time_complex":  lambda p: len(p["range_safe_date_columns"]) >= 1 and len(p["having_friendly_columns"]) >= 1,
"groupby_having": lambda p: len(p["having_friendly_columns"]) >= 1,
"agg_simple":     lambda p: len(p["aggregatable_columns"]) >= 1,
```

这就是为什么第六节"可用表"列的数字常小于第四节的池大小（P5 299 → time_complex 143）。

配额未满时的处理顺序：① 放宽表池条件重算 → ② 把缺口匀给同难度的其他任务 → ③ 下调该任务配额并在文档中记录实际值。**不允许通过提高单表密度来凑数**——6.4 节的三处调整就是按这个顺序做的。

### 11.3 必须单独盯的三项

1. **HAVING 空结果率。** 如果 `GROUP BY + HAVING` 类样本的空结果率超过 10%，说明阈值反推没生效，要停下来修管道而不是继续生成。
2. **P4 池和 P5 池的模板重复率。** P4 只有 571 张表却要承担 2,100 条 Hard 样本（密度 1.93 / 1.75），`time_complex` 更只有 143 张表承担 250 条（密度 1.75）——这三项是全管道最容易出现模板雷同的地方。要按"表 + 分组列 + 聚合函数"三元组统计去重率，同一张表的两条样本必须换分组列或换聚合指标。
3. **字段语义错误率。** 匿名字段 `col_N` 的业务含义映射失败会直接导致语义错误，且执行验证发现不了。人工抽检时这一项要单独计分。

## 十三、本文档确定的结论

1. 数据库是 5,013 张表的单文件 SQLite，**全库 0 个外键、表间无可信关联**。因此只做单表查询，禁止 JOIN、UNION 和跨表子查询，静态校验阶段按表引用集合强制拦截，验收容忍度为 0。`possible_join_columns` 字段是字段同名造成的假信号，不得使用。
2. 配额不按表数量乘，而是**总量固定 30,000 条，按表能力池摊到各难度各任务**。
3. 难度分布 Easy 12,000 / Medium 12,000 / Hard 6,000，28 个任务的配额见第六节，**已实算配满、零密度违例**：覆盖 4,987 / 5,013 张表，单表最多 10 条，覆盖表均摊 6.02 条。
4. **"从哪些表生成"的答案是 `synthesis_tasks.jsonl`**（28,051 行工单，每行 `表 + 任务 + 条数`），由 `build_table_pools.py` → `allocate_quota.py` 两步生成。合成管道遍历这个文件即可，不让模型自己挑表挑列。
5. 字段业务含义**全库 100% 可用**（5,013/5,013 表头列数零偏差），推翻了原方案"匿名字段难映射"的假设。`semantic_known` 判定保留但实际不触发降级。
6. 真正的瓶颈有三个，都不是表的数量：
   - **单表最多 100 行、中位数 26 行** —— `LIMIT` 上界、分组数、`HAVING` 阈值都必须按真实数据动态确定
   - **可 SUM 的列只有 944 张表（18.8%）** —— 大量数值列是比率、排名、编号，加总无意义
   - **可靠时间列只有 430 张表（8.6%）** —— 日期格式极脏，时间类任务总量因此从原方案 2,100 条下调到 1,150 条
   - 最难的 P4 池（分组 + 多聚合 + HAVING 全具备）只有 **571 张表**，承担 2,100 条 Hard 样本
7. 分三阶段推进：1,000 条冒烟 → 5,000 条中试 → 30,000 条扩量，每阶段有明确准入条件，不达标不扩量。
8. 预计需生成 38,000 ~ 45,000 条候选才能得到 30,000 条合格样本。
9. 字段映射失败的表降级使用，禁止参与 SUM / AVG / 分组统计。
