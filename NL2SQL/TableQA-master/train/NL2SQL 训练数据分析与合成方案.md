# NL2SQL 训练数据分析与合成方案

## 一、项目背景与目标

当前 NL2SQL 训练数据以单表查询为主，整体查询结构相对简单，复杂 SQL 类型覆盖不足。

为了提升模型对不同查询场景的理解和 SQL 生成能力，需要先分析现有数据的结构分布，明确训练数据的薄弱环节，再结合真实数据库中的表结构和数据，合成具有针对性的训练样本。

本阶段的目标是：

1. 分析现有 NL2SQL 数据的 SQL 结构与难度分布。
2. 明确当前训练数据覆盖不足的查询类型。
3. 从真实数据库中筛选适合合成样本的候选表。
4. 制定基于单表查询的合成任务规划。
5. 通过 SQL 执行验证和结构统计，保证合成数据的有效性。

本方案聚焦单表查询，不涉及多表 JOIN。

## 三、现有数据的主要问题

结合 SQL 结构分析结果，当前数据主要存在以下不足。

### 3.1 查询类型集中于条件筛选

现有样本全部包含 WHERE，说明数据主要围绕条件过滤展开。

虽然已有 AND、OR 和部分聚合查询，但整体仍以基础查询为主。

### 3.2 分组统计能力覆盖不足

现有数据中没有 GROUP BY 和 HAVING。

模型缺少通过训练数据学习以下查询模式的机会：

* 按类别统计记录数量。
* 按类别计算数值总和或平均值。
* 对分组后的统计结果进行条件过滤。
* 对分组结果进行排序。

### 3.3 排序和结果控制能力覆盖不足

现有数据中没有 ORDER BY、LIMIT 和 DISTINCT。

因此，以下查询类型缺少直接训练样本：

* 查询数值最高或最低的记录。
* 查询排名前 N 的记录。
* 按指定字段升序或降序排列。
* 查询某字段的不同取值。

### 3.4 复杂条件表达覆盖不足

现有数据虽然包含 AND 和 OR，但没有 IN、LIKE、BETWEEN、NOT 等结构。

可以考虑补充：

* 多个候选值匹配。
* 字符串模糊查询。
* 数值或日期范围筛选。
* 条件取反。
* 多种条件组合使用。

### 3.5 SQL 组合能力有待增强

现有数据中缺少 GROUP BY、ORDER BY、LIMIT 等结构，也缺少它们与 WHERE、聚合函数组合使用的样本。

因此，后续合成数据不仅要补充单独的 SQL 语法，还需要补充多个子句组合使用的查询。

### 4.2 候选表的作用

候选表不是最终训练样本，而是后续合成数据的数据来源。

后续可以从候选表中随机选择少量表，根据真实字段和数据生成单表查询样本。

不需要对全部 1,000 张表逐一生成数据，也不需要每张表都覆盖所有 SQL 类型。

### 4.3 单表查询约束

本阶段仅生成单表查询。

每条合成 SQL 只涉及一张业务表，不生成 JOIN、多表关联或跨表查询。

即使生成复杂 SQL，也应在同一张表内组合使用 WHERE、GROUP BY、HAVING、ORDER BY、LIMIT 等子句。

### 4.4 候选表的使用原则

候选表筛选结果主要用于确定可用的数据来源。

具体生成哪种查询，应根据所选表的真实字段和数据决定：

* 有明确类别字段的表，可以考虑条件筛选和分组统计。
* 有含义明确的数值字段，可以考虑数值比较和聚合。
* 有有效日期字段的表，可以考虑日期范围筛选和时间排序。
* 有多个有效查询字段的表，可以考虑多条件组合。
* 数据行数足够的表，可以考虑排序、LIMIT 和统计查询。

不能仅根据字段类型推断字段业务含义。例如，数值字段不一定代表金额或数量，也可能是编号、日期编码或分类标识。

## 五、合成数据的总体思路

### 5.1 合成原则

合成数据遵循以下原则：

1. 以现有训练数据分析结果为依据，优先补充缺失的 SQL 结构。
2. 仅生成单表查询，不生成 JOIN。
3. 从候选表中随机抽取少量表，避免依赖固定表集合。
4. 根据真实字段含义和数据分布决定可生成的查询类型。
5. 生成 SQL 后必须执行验证。
6. 确保自然语言问题与 SQL 的查询含义一致。
7. 合成后重新进行 SQL 结构统计，检查数据覆盖是否改善。

### 5.2 合成任务类型

建议将合成任务分为以下几类。

#### A. 基础条件筛选

目标：增强模型对字段选择和条件过滤的理解。

包括：

* 单条件筛选。
* AND 多条件筛选。
* OR 条件筛选。
* IN 多值筛选。
* LIKE 模糊匹配。
* BETWEEN 范围筛选。
* 多字段 SELECT。

#### B. 聚合查询

目标：补充统计类 SQL。

包括：

* COUNT。
* SUM。
* AVG。
* MAX。
* MIN。

聚合函数应根据字段实际含义选择。例如，对没有业务意义的编号字段不应直接生成 AVG 或 SUM。

#### C. 分组统计

目标：补充分组查询能力。

包括：

* GROUP BY。
* GROUP BY + 聚合函数。
* GROUP BY + HAVING。
* 分组结果排序。

分组字段应具有合理的类别意义，并且需要有足够的不同取值。

#### D. 排序与结果控制

目标：补充排序和结果集控制能力。

包括：

* ORDER BY ASC。
* ORDER BY DESC。
* ORDER BY + LIMIT。
* Top-K 查询。
* DISTINCT。

#### E. 多子句组合查询

目标：训练模型组合多个 SQL 子句。

包括：

* WHERE + ORDER BY。
* WHERE + LIMIT。
* WHERE + 聚合函数。
* WHERE + GROUP BY。
* WHERE + GROUP BY + HAVING。
* WHERE + ORDER BY + LIMIT。

组合查询应建立在单项结构正确的基础上，避免为了增加复杂度而生成不合理 SQL。

## 七、合成数据生成流程

### 7.1 总体流程

1. 读取候选表清单。
2. 随机选择一张候选表。
3. 获取该表真实 schema 和必要的数据样例。
4. 根据字段含义判断支持的查询类型。
5. 按任务配额选择合成目标。
6. 生成自然语言问题和 SQL。
7. 执行 SQL 并进行一致性校验。
8. 保存有效样本。
9. 统计合成数据的 SQL 结构分布。
10. 根据结果调整下一轮合成配额。

### 7.2 样本校验要求

每条合成样本至少需要完成以下检查：

| 检查项         | 说明                     |
| ----------- | ---------------------- |
| SQL 可执行性    | SQL 能在目标 SQLite 数据库中执行 |
| 表名正确性       | 仅引用指定的单张表              |
| 字段正确性       | SQL 中的字段真实存在           |
| 问题与 SQL 一致性 | 自然语言问题准确描述 SQL 查询内容    |
| 数据值有效性      | 条件值来自真实数据或经过合理验证       |
| 结果合理性       | 执行结果与问题意图一致            |
| 结构标签        | 记录 SQL 中实际出现的结构类型      |

需要特别注意：SQL 执行成功并不代表自然语言问题与 SQL 语义一定一致，因此还需要单独进行语义校验。

## 八、合成数据的效果评估

合成完成后，应使用与原始数据相同或兼容的 SQL 结构分析方法进行统计。

重点关注以下指标：

### 8.1 数据规模

* 合成样本总数。
* SQL 执行通过率。
* 语义校验通过率。
* 各任务类型的有效样本数量。

### 8.2 SQL 结构覆盖率

重点检查合成后是否增加了以下结构：

* GROUP BY。
* HAVING。
* ORDER BY。
* LIMIT。
* DISTINCT。
* IN。
* LIKE。
* BETWEEN。
* 多子句组合。

### 8.3 数据质量

重点检查：

* 是否存在重复问题。
* 是否存在 SQL 相同但问题含义不同的错误样本。
* 是否存在问题与 SQL 不一致的样本。
* 是否存在字段含义推断错误。
* 是否存在执行成功但结果不符合问题意图的样本。

### 8.4 模型效果

合成数据加入训练后，应在独立验证集上比较：

* 原始 SFT 模型。
* 加入合成数据后的 SFT 模型。
* 后续如开展 GRPO，再比较 GRPO 前后的表现。

评估时应同时观察总体执行准确率和不同 SQL 结构的分层表现，避免只看整体指标而忽略某类查询能力退化。

### 8.5 合成样本数量与训练集采样方案

#### 8.5.1 现有数据分布

当前原始训练数据共 41,522 条：

| 难度 | 样本数量 | 占比 |
|---|---:|---:|
| Easy | 31,205 | 75.15% |
| Medium | 10,317 | 24.85% |
| Hard | 0 | 0% |
| **合计** | **41,522** | **100%** |

现有数据以 Easy 和 Medium 为主，Easy 占比约 75%。同时，原始 SQL 结构主要集中在 WHERE 条件筛选，GROUP BY、HAVING、ORDER BY、LIMIT 等结构缺失。

因此，本阶段不应继续大量增加基础筛选题，而应重点补充原始数据中缺少的 SQL 结构与组合能力。

#### 8.5.2 第一轮训练集目标规模

建议第一轮训练集按照 Easy、Medium、Hard 分层构建，目标规模为 **25,000 条**：

| 难度 | 目标数量 | 占比 | 数据来源与处理方式 |
|---|---:|---:|---|
| Easy | 10,000 | 40% | 从原始 Easy 中分层采样，保留其他原始样本 |
| Medium | 10,000 | 40% | 优先使用原始 Medium，不足部分再补充合成样本 |
| Hard | 5,000 | 20% | 主要通过合成数据补充，经过质量验收后纳入 |
| **合计** | **25,000** | **100%** | |

该方案不是删除原始数据，而是控制第一轮实际参与训练的样本数量。未被采样到的原始数据继续保留，可用于后续实验或调整训练采样比例。

#### 8.5.3 合成样本数量规划

根据上述训练集目标，初步规划合成数据如下：

| 难度 | 训练目标 | 原始可用规模 | 初步合成规划 |
|---|---:|---:|---:|
| Easy | 10,000 | 31,205 | 暂不大量合成，仅补充新表、新字段覆盖 |
| Medium | 10,000 | 10,317 | 视原始数据清洗结果补充，重点覆盖缺失 SQL 结构 |
| Hard | 5,000 | 0 | 计划合成并验收 5,000 条 |
| **合计** | **25,000** | | |

说明：

1. 原始 Medium 经过清洗、去重后，实际可用数量可能低于 10,000 条。
2. Medium 的合成数量根据清洗后的有效样本量确定，不预先固定。
3. Hard 计划合成 5,000 条合格样本，若合成验收通过率不足，应继续生成和筛选，不能将未通过验收的样本直接加入训练集。
4. Easy 不需要大量合成，但应关注新表、新字段和不同表达方式的覆盖情况。
5. 上述数量为第一轮实验目标，后续可根据验证集结果调整。

#### 8.5.4 合成数据任务设计

合成样本重点补充原始数据中缺失或覆盖不足的 SQL 结构。

| 任务类型 | 主要覆盖内容 | 目标难度 |
|---|---|---|
| 多条件筛选 | 多个 WHERE 条件、AND、OR、条件组合 | Easy / Medium |
| 聚合查询 | COUNT、SUM、AVG、MAX、MIN | Medium |
| 分组统计 | GROUP BY、分组计数、分组聚合 | Medium |
| 分组过滤 | GROUP BY + HAVING | Hard |
| 排序与结果限制 | ORDER BY、LIMIT、Top-N 查询 | Medium / Hard |
| 多子句组合 | WHERE + GROUP BY + HAVING + ORDER BY + LIMIT | Hard |

所有合成任务仍限定为单表查询，不生成多表 JOIN。

合成时应根据真实表结构、字段含义和数据分布决定任务类型，不能仅根据字段类型推断业务含义。例如，数值字段可能是编号、日期编码或分类编码，不应在未确认语义的情况下直接进行 SUM 或 AVG。

#### 8.5.5 数据清洗与训练集构建流程

建议采用以下流程：

1. **保留原始数据**：不因 Easy 占比高而直接删除原始样本。
2. **原始数据清洗**：检查无效 SQL、重复样本及问题与 SQL 语义不一致的样本。
3. **难度重新标注**：使用统一规则对原始数据和合成数据进行难度标注。
4. **合成数据验收**：检查 SQL 执行结果、问题与 SQL 的语义一致性、字段语义及重复情况。
5. **分层采样**：从有效数据池中构建 Easy 10,000 条、Medium 10,000 条、Hard 5,000 条的第一轮训练集。
6. **独立验证**：使用固定验证集，分别评估基础筛选、聚合、分组、排序、结果限制及多子句组合等能力。
7. **迭代调整**：根据各类 SQL 结构的执行准确率和错误分布，调整采样比例及后续合成任务。

#### 8.5.6 阶段性结论

第一轮训练集建议以 **25,000 条**为目标，其中 Easy 10,000 条、Medium 10,000 条、Hard 5,000 条。

原始数据全部保留，在训练集构建阶段进行清洗和分层采样。合成数据重点补充 Hard 类型，以及原始数据中覆盖不足的分组、排序、结果限制和多子句组合。

该方案能够降低 Easy 样本在训练中的占比，同时保留基础查询能力，并为复杂 SQL 结构提供更多训练信号。最终训练集规模和采样比例，应根据合成数据质量及独立验证集上的分结构评估结果进一步确定。

## 8.6 训练集构建与合成数据规划

### 8.6.1 目标与原则

当前原始 NL2SQL 数据集共约 4.15 万条，但样本主要集中在简单单表筛选查询，SQL 结构覆盖不足。继续大量使用此类样本训练，可能无法有效提升模型对复杂查询的生成能力。

因此，本阶段不以扩大数据规模为目标，而是围绕模型能力短板，构建一套结构覆盖更充分、难度分布合理、质量可控的训练集。

本阶段计划构建 **2500 条候选训练样本**，按照 Easy、Medium、Hard 三个难度等级进行组织。

数据构建遵循以下原则：

1. **单表查询约束**：所有训练样本均限定为单表查询，不生成多表 JOIN。
2. **能力覆盖优先**：优先补充现有数据缺失的 SQL 结构及其组合。
3. **难度分级明确**：难度由查询逻辑、SQL 结构组合和语义映射复杂度共同决定，不单纯依据 SQL 长度。
4. **真实 Schema 约束**：所有问题和 SQL 必须基于实际数据库表结构及字段语义生成。
5. **质量优先于数量**：合成样本必须经过执行验证、语义检查和去重处理。
6. **保留必要基础样本**：简单查询仍用于维持基础能力，但不再作为训练集主体。

### 8.6.2 样本数量与难度分布

本阶段计划构建 2500 条候选样本，具体分布如下：

| 难度等级   |     目标数量 |       占比 | 主要训练目标             |
| ------ | -------: | -------: | ------------------ |
| Easy   |     1000 |      40% | 基础查询能力及常见 SQL 结构   |
| Medium |     1000 |      40% | 多条件查询及中等复杂度 SQL 组合 |
| Hard   |      500 |      20% | 多结构组合及复杂查询逻辑       |
| **合计** | **2500** | **100%** |                    |

上述数量为候选训练集的目标规模。最终纳入训练的数据应以质量校验结果为准，不因数量不足而降低样本质量要求。

### 8.6.3 Easy 样本设计

Easy 样本共计划构建 1000 条，主要覆盖基础查询结构及常见查询需求。

| SQL 类型   | 训练内容                  |
| -------- | --------------------- |
| 基础 WHERE | 单条件筛选、等值与比较条件         |
| 多条件筛选    | AND、OR 及常见条件组合        |
| 简单聚合     | COUNT、SUM、AVG、MIN、MAX |
| 排序查询     | ORDER BY、升序与降序        |
| Top-K 查询 | ORDER BY 与 LIMIT 组合   |
| 去重查询     | DISTINCT              |
| 范围查询     | BETWEEN、IN、LIKE 等适用结构 |

Easy 样本重点考查模型对自然语言查询意图、字段和值的映射能力，以及基础 SQL 结构的正确生成能力。

### 8.6.4 Medium 样本设计

Medium 样本共计划构建 1000 条，重点覆盖单表查询中的多条件逻辑和中等复杂度 SQL 结构。

| SQL 类型 | 训练内容                                       |
| ------ | ------------------------------------------ |
| 复杂条件筛选 | 多个 AND、OR 条件组合，必要时使用括号明确逻辑                 |
| 分组统计   | GROUP BY 与聚合函数组合                           |
| 分组后过滤  | GROUP BY 与 HAVING 组合                       |
| 聚合与筛选  | WHERE 与聚合函数组合                              |
| 排序与聚合  | 聚合结果排序、分组结果排序                              |
| 去重与统计  | DISTINCT 与聚合查询组合                           |
| 多结构组合  | WHERE、GROUP BY、HAVING、ORDER BY、LIMIT 等结构组合 |

Medium 样本应体现真实查询需求，不应仅通过增加 WHERE 条件数量来提高难度。

### 8.6.5 Hard 样本设计

Hard 样本共计划构建 500 条，重点覆盖复杂查询意图、多个 SQL 结构组合以及容易产生歧义的查询场景。

| SQL 类型  | 训练内容                                     |
| ------- | ---------------------------------------- |
| 多结构组合   | WHERE、GROUP BY、HAVING、ORDER BY、LIMIT 等组合 |
| 复杂分组统计  | 多字段分组、多个聚合指标及分组结果筛选                      |
| 复杂条件逻辑  | 多层 AND、OR 组合及边界条件                        |
| 聚合结果比较  | 根据聚合结果进行筛选、排序或 Top-K 查询                  |
| 语义歧义消解  | 相似字段、相似指标及不同统计口径的区分                      |
| 边界与异常场景 | NULL、空结果、重复值、时间边界等适用场景                   |

Hard 样本的难度应来自查询语义和逻辑复杂度，而不是人为堆叠 SQL 语句或使用不符合业务场景的结构。

### 8.6.6 SQL 结构覆盖要求

训练集构建过程中，应重点关注以下 SQL 结构及组合：

| SQL 结构              | 覆盖要求                     |
| ------------------- | ------------------------ |
| WHERE               | 保留必要基础样本，避免成为训练集绝对主体     |
| AND / OR            | 覆盖多条件及组合逻辑               |
| 聚合函数                | 覆盖 COUNT、SUM、AVG、MIN、MAX |
| GROUP BY            | 补充分组统计能力                 |
| HAVING              | 补充分组后的条件过滤               |
| ORDER BY            | 覆盖单字段、多字段及排序方向           |
| LIMIT               | 覆盖 Top-K 查询              |
| DISTINCT            | 覆盖去重查询                   |
| IN / LIKE / BETWEEN | 根据字段类型和实际语义生成            |
| 多结构组合               | 重点补充复杂查询能力               |

上述结构不要求机械地平均分配。具体配额应结合业务场景、模型基线评测结果和 SQL 结构适用性确定。

### 8.6.7 合成数据生成流程

合成数据按照以下流程构建：

1. **Schema 选择**：从候选数据库表中选择适合生成目标查询的表。
2. **字段语义分析**：识别字段类型、字段含义及可执行的查询操作。
3. **查询意图设计**：根据目标 SQL 结构设计自然语言问题。
4. **SQL 生成**：生成与问题对应的单表 SQL。
5. **难度标注**：依据查询逻辑、SQL 结构和语义复杂度标记难度等级。
6. **执行验证**：在对应数据库中执行 SQL，检查语法及运行情况。
7. **语义校验**：检查自然语言问题是否准确表达 SQL 的查询意图。
8. **去重检查**：检查问题、SQL、结构模板及语义是否重复。
9. **质量筛选**：仅保留通过校验的样本，纳入候选训练集。

### 8.6.8 数据质量控制

合成样本必须满足以下要求：

* SQL 仅访问指定的单张业务表，不包含多表 JOIN。
* SQL 中引用的表名、字段名必须存在于真实 Schema。
* 聚合函数应符合字段类型和业务语义，不对不适合统计的字段强行聚合。
* 自然语言问题与 SQL 的筛选条件、统计口径、排序要求和返回字段保持一致。
* 对 SQL 执行成功但语义不匹配的样本，应判定为无效样本。
* 对同一 SQL 模板仅替换常量形成的大量相似样本，应进行比例控制。
* 对 NULL、空结果、重复值和时间边界等场景，应根据实际业务需求设计。
* 不得仅以 SQL 执行成功作为样本正确性的唯一判断依据。

### 8.6.9 原始数据使用策略

现有约 4.15 万条原始样本作为基础数据池保留，不直接全部纳入最终训练集。

首先对原始样本进行 SQL 解析、执行验证、语义检查和重复性分析，再根据目标结构分布筛选可用样本。

对于原始数据中覆盖充分、质量较高的查询类型，可适量保留；对于缺失或覆盖不足的 SQL 结构，优先通过定向合成进行补充。

模板重复率仅用于发现潜在冗余，不能直接作为删除样本的依据。相同 SQL 模板可能对应不同表、字段、业务语义或查询目标，应结合实际内容判断是否重复。

### 8.6.10 本阶段交付目标

本阶段最终形成一套约 2500 条的候选训练集，并完成以下工作：

1. 建立 Easy、Medium、Hard 三档样本。
2. 补充原始数据中覆盖不足的 SQL 结构。
3. 控制各类 SQL 结构及其组合的分布。
4. 完成 SQL 执行验证与问题—SQL 语义一致性检查。
5. 完成重复样本检查和数据质量筛选。
6. 输出各难度等级及各 SQL 结构的实际样本统计。

最终训练集的目标不是追求 SQL 结构数量完全平均，而是确保模型训练数据能够覆盖目标业务中的主要查询能力，并针对基座模型的实际错误类型进行补充。

# 8.7 数据合成流水线思路

## 8.7.1 章节目标

现有 NL2SQL 训练数据主要集中在单表查询和简单 `WHERE` 条件，SQL 结构相对单一。若直接扩大现有数据规模，可能只是增加相似样本，难以有效提升模型对复杂查询的理解与生成能力。

因此，数据合成的核心目标不是单纯增加样本数量，而是围绕真实数据库 Schema 和业务语义，构建结构多样、语义正确、可执行、可验证的 NL2SQL 训练数据。

本方案采用“**任务规划 → SQL 生成 → 数据库执行 → 自然语言生成 → 语义校验 → 去重入库**”的流水线方式，逐步构建高质量合成数据集。

本阶段遵循以下原则：

1. **单表查询优先**：每条 SQL 仅访问一张目标表，不生成多表 JOIN。
2. **基于真实 Schema**：表名、字段名、字段类型必须来自真实数据库，不允许模型虚构字段。
3. **业务语义约束**：字段是否支持求和、平均值、分组等操作，需要结合字段含义判断，不能仅依赖数据类型。
4. **结构覆盖优先**：重点补充现有数据缺少的 SQL 结构，而不是重复生成简单条件查询。
5. **执行结果可验证**：生成的 SQL 必须通过数据库执行验证；执行成功不代表语义正确，还需要独立校验。
6. **分阶段扩量**：先进行小规模试生成和人工抽检，验证质量后再扩大数据规模。

## 8.7.2 整体流水线

```text
真实数据库 / Schema / 字段元数据
                │
                ▼
        1. Schema 信息整理
                │
                ▼
        2. 查询任务规划
                │
                ▼
        3. SQL 候选生成
                │
                ▼
        4. SQL 规则校验
                │
                ▼
        5. 数据库执行验证
                │
                ▼
        6. 自然语言问题生成
                │
                ▼
        7. 问题与 SQL 语义校验
                │
                ▼
        8. 去重、质量筛选
                │
                ▼
        9. 数据集入库与统计
```

各阶段职责相互独立。某一阶段失败时，样本进入失败记录，不应直接进入最终训练集。

## 8.7.3 第一阶段：Schema 信息整理

数据合成首先需要将数据库结构转换为模型可理解的上下文信息。

每张表至少需要整理以下内容：

| 信息     | 说明                  |
| ------ | ------------------- |
| 表名     | 数据库中的真实表名           |
| 表描述    | 表所表达的业务主题           |
| 字段名    | 数据库中的真实字段名          |
| 字段类型   | TEXT、INTEGER、REAL 等 |
| 字段业务含义 | 字段代表的业务指标或维度        |
| 字段示例值  | 用于辅助理解字段内容          |
| 字段统计信息 | 空值率、唯一值数量、数值范围等     |
| 允许操作   | 字段可用于过滤、排序、聚合或分组等操作 |

### 8.7.3.1 字段映射

部分数据集中的数据库字段可能使用 `col_1`、`col_2` 等匿名名称，而业务元数据中使用的是中文表头。

需要通过明确的字段映射关系，将数据库字段与业务含义对应起来。

例如：

```json
{
  "table_name": "land_transfer",
  "columns": [
    {
      "column_name": "col_1",
      "business_name": "城市",
      "type": "TEXT",
      "allowed_operations": ["filter", "group_by"]
    },
    {
      "column_name": "col_2",
      "business_name": "规划建筑面积",
      "type": "REAL",
      "unit": "万平方米",
      "allowed_operations": ["filter", "sum", "avg", "order_by"]
    }
  ]
}
```

字段映射必须来源于真实数据或经过确认的元数据，不能仅根据字段顺序进行推断。

如果字段映射不明确，则应限制该字段参与依赖业务含义的复杂任务，避免生成语义错误的 SQL。

### 8.7.3.2 字段操作约束

字段类型不能直接决定其业务操作。

例如：

* 数值字段可能是金额、面积、比例、编号或评分。
* 文本字段可能是城市、类别、名称或日期字符串。
* 编号字段即使是整数，也不一定适合求和或求平均值。
* 比例字段可以参与过滤、排序或平均值计算，但通常不适合直接求和。

因此，应在元数据中记录字段允许执行的操作，并在任务规划和 SQL 校验阶段共同使用。

## 8.7.4 第二阶段：查询任务规划

任务规划阶段不直接生成 SQL，而是先确定本次需要合成哪一种查询任务。

这样可以避免模型始终生成简单的 `WHERE` 查询，也便于控制数据集中的难度比例和 SQL 结构覆盖率。

### 8.7.4.1 难度分层

初始数据集可按 Easy、Medium、Hard 三个层级进行规划。

| 难度     | 查询特征                | 示例结构                              |
| ------ | ------------------- | --------------------------------- |
| Easy   | 单表简单过滤、排序或限制结果数量    | `WHERE`、`ORDER BY`、`LIMIT`        |
| Medium | 多条件组合、聚合计算、分组统计     | `AND`、`OR`、`SUM`、`AVG`、`GROUP BY` |
| Hard   | 多条件组合下的分组统计、聚合结果过滤等 | `GROUP BY` + `HAVING`、复杂条件组合      |

难度划分应根据 SQL 结构和业务理解要求确定，而不是仅根据 SQL 长度判断。

### 8.7.4.2 初始数据规模

在目标合成规模为 30,000 条的情况下，可先采用以下计划作为初始配比：

| 难度     |   比例 |   目标数量 |
| ------ | ---: | -----: |
| Easy   |  40% | 12,000 |
| Medium |  40% | 12,000 |
| Hard   |  20% |  6,000 |
| 合计     | 100% | 30,000 |

该配比是目标计划，不代表最终合格数据一定能够达到对应数量。实际生成过程中，应以通过全部校验的有效样本数为准。

同时，需要单独统计 SQL 结构覆盖情况。难度比例均衡，并不意味着查询结构已经均衡。

### 8.7.4.3 查询结构规划

建议将 SQL 结构拆分为可组合的任务类型，例如：

* 单条件过滤
* 多条件 `AND`
* 多条件 `OR`
* 混合条件组合
* 排序与结果数量限制
* 单字段聚合
* 多字段聚合
* 分组统计
* 分组后条件过滤
* 去重查询

每个任务需要结合字段类型和业务含义进行筛选。例如，只有具备合理业务含义的字段才能参与 `SUM`、`AVG` 或 `GROUP BY`。

任务规划阶段应记录目标难度、目标 SQL 结构、目标字段及约束条件，作为后续 SQL 生成的输入。

## 8.7.5 第三阶段：SQL 候选生成

根据任务规划结果，向模型提供以下信息：

1. 数据库 Schema。
2. 字段业务描述和允许操作。
3. 字段示例值及统计信息。
4. 当前查询任务要求。
5. SQL 方言要求。
6. 单表查询限制。
7. 输出格式要求。

模型根据任务生成 SQL 候选，并同时输出生成依据和结构标签，便于后续校验和统计。

建议每次生成多个候选，而不是只生成一条 SQL。候选数量可根据模型推理成本和任务难度调整。

### 8.7.5.1 SQL 生成约束

生成阶段至少应明确以下规则：

* 仅允许查询指定目标表。
* 不允许使用 `JOIN`。
* 不允许引用 Schema 中不存在的字段。
* 不允许虚构表名、字段名或业务含义。
* 聚合操作必须符合字段语义。
* 分组查询中的非聚合字段必须符合 SQL 分组规则。
* 生成的 SQL 必须符合指定数据库方言。
* 仅生成查询语句，不生成数据修改语句。

模型输出建议采用结构化 JSON，包含：

```json
{
  "table_name": "目标表名",
  "difficulty": "medium",
  "features": ["group_by", "sum"],
  "used_columns": ["城市", "土地出让金"],
  "query_plan": "按城市分组，统计各城市土地出让金总额",
  "sql": "SELECT ..."
}
```

以上内容仅为输出结构示例，实际字段名和 SQL 必须来自真实 Schema。

## 8.7.6 第四阶段：SQL 规则校验

SQL 生成后，首先进行静态规则校验。该阶段不依赖数据库执行结果，主要检查 SQL 是否符合预先定义的约束。

建议校验以下内容：

| 校验项     | 校验要求                      |
| ------- | ------------------------- |
| SQL 语法  | 能够被目标 SQL 方言解析            |
| 查询类型    | 仅允许 SELECT 查询             |
| 表数量     | 仅允许访问一张目标表                |
| 表名合法性   | 必须为指定目标表                  |
| 字段合法性   | 所有字段必须存在于真实 Schema        |
| JOIN 检查 | 不允许出现 JOIN                |
| 子查询规则   | 按当前任务范围决定是否允许             |
| 聚合规则    | 聚合操作必须符合字段业务含义            |
| 分组规则    | 检查 GROUP BY 与 SELECT 字段关系 |
| 难度标签    | SQL 结构与规划难度保持一致           |

静态校验失败的 SQL 不进入数据库执行阶段，应记录具体失败原因。

## 8.7.7 第五阶段：数据库执行验证

通过静态校验的 SQL，进入真实数据库执行阶段。

执行验证主要确认：

1. SQL 能否在目标数据库中执行。
2. SQL 是否引用了不存在的字段或表。
3. SQL 是否存在类型不匹配等执行错误。
4. SQL 是否能够返回结果。
5. 返回结果是否符合任务预期。

建议在只读连接或只读副本上执行合成 SQL，并设置执行超时和资源限制，避免异常 SQL 影响原始数据库。

需要注意：

**SQL 执行成功，只能说明语法和执行层面基本可用，不能证明 SQL 与自然语言问题语义一致。**

例如，某条 SQL 可以正常执行，但可能使用了错误的统计字段，或者遗漏了问题中要求的筛选条件。因此，数据库执行验证只是质量控制的一部分。

## 8.7.8 第六阶段：自然语言问题生成

SQL 通过执行验证后，再根据 SQL 及其查询意图生成自然语言问题。

采用“先生成 SQL，再生成问题”的方式，可以减少问题和 SQL 在字段、条件、统计方式上的偏差。

自然语言问题应满足：

* 准确表达 SQL 中的筛选条件。
* 准确表达统计指标和统计方式。
* 准确表达分组维度。
* 准确表达排序和结果数量限制。
* 不增加 SQL 中不存在的条件。
* 不遗漏 SQL 中已有的重要条件。
* 使用符合业务场景的自然表达。
* 避免直接照抄 SQL 语法。

例如，SQL 中包含按城市分组并统计土地出让金总额，则问题应明确表达“按城市统计土地出让金总额”，不能只写成“查询土地出让金”。

生成自然语言问题时，应尽量使用字段的业务名称，而不是数据库内部的匿名字段名。

## 8.7.9 第七阶段：问题与 SQL 语义校验

语义校验是整个数据合成流水线中的关键环节。

该阶段需要独立检查自然语言问题是否能够准确对应 SQL，而不是只判断 SQL 是否可执行。

建议从以下维度进行校验：

| 校验维度 | 检查内容                     |
| ---- | ------------------------ |
| 表与字段 | 问题涉及的业务对象是否对应 SQL 中的表和字段 |
| 筛选条件 | 问题中的条件是否完整出现在 SQL 中      |
| 条件关系 | AND、OR 等逻辑关系是否一致         |
| 聚合方式 | 求和、平均值、最大值等统计方式是否一致      |
| 分组维度 | 问题要求的分组维度是否正确            |
| 排序要求 | 升序、降序及排序字段是否一致           |
| 数量限制 | 问题中的数量限制是否对应 LIMIT 等语句   |
| 业务语义 | SQL 是否符合字段和指标的实际含义       |

语义校验可以由独立模型完成，但模型判断不能被视为绝对可靠。建议结合规则校验、数据库执行、抽样人工审核等方式进行质量控制。

对于校验不通过的样本，应记录具体问题，并根据情况重新生成 SQL、重新生成问题或直接丢弃。

## 8.7.10 第八阶段：去重与质量筛选

完成校验后，对候选样本进行去重和质量筛选。

去重时不应只依赖自然语言问题文本，也不应简单地将所有相同 SQL 模板视为重复样本。

建议分层处理：

### 8.7.10.1 完全重复

问题文本和 SQL 完全相同的样本，只保留一条。

### 8.7.10.2 SQL 结构重复

对 SQL 进行规范化处理，例如统一关键字大小写、格式和部分字面量表达，识别结构相同的 SQL。

结构重复可以作为统计指标，但不一定需要全部删除。不同字段、不同业务条件或不同自然语言表达，可能具有独立训练价值。

### 8.7.10.3 语义重复

对于问题表达不同、SQL 结构相同但实际查询意图高度一致的样本，可以通过语义相似度或人工抽检进行识别。

去重目标不是让每条 SQL 都具有完全不同的结构，而是减少无意义的重复，保留有价值的表达多样性和业务覆盖。

## 8.7.11 第九阶段：数据集入库与统计

通过所有校验的样本进入最终合成数据集。

建议每条数据至少保留以下信息：

```json
{
  "question": "自然语言问题",
  "sql": "SELECT ...",
  "table_name": "目标表名",
  "difficulty": "medium",
  "features": ["group_by", "sum"],
  "used_columns": ["字段A", "字段B"],
  "query_plan": "查询意图说明",
  "execution_status": "success",
  "semantic_check_status": "pass",
  "source": "synthetic",
  "version": "v1"
}
```

其中，`execution_status` 和 `semantic_check_status` 应由实际校验流程写入，不应由 SQL 生成模型自行声明。

数据集入库后，应持续统计：

* 各难度的有效样本数量。
* 各 SQL 结构的覆盖数量。
* 各表和字段的覆盖情况。
* SQL 静态校验通过率。
* SQL 执行成功率。
* 语义校验通过率。
* 重复样本比例。
* 各阶段失败原因分布。

通过统计结果判断当前合成数据是否达到预定目标，并据此调整任务规划策略。

## 8.7.12 质量控制与迭代策略

数据合成不应一次性生成全部目标数据，而应采用小规模试验、质量评估、逐步扩量的方式。

### 第一阶段：小规模验证

先生成少量样本，重点检查：

* Schema 信息是否完整。
* 字段映射是否正确。
* SQL 是否符合单表约束。
* 复杂 SQL 是否能够正确执行。
* 自然语言问题是否准确表达 SQL。
* 语义校验能否发现典型错误。

### 第二阶段：结构覆盖验证

确认基础质量后，逐步扩大生成规模，并检查不同 SQL 结构的覆盖情况。

如果某类结构生成失败率较高，应优先调整该类任务的字段选择规则、提示词或校验逻辑，而不是直接增加生成次数。

### 第三阶段：规模扩展

当小规模数据的执行通过率和语义正确率达到预设要求后，再逐步扩大生成规模，直至接近目标数量。

### 第四阶段：训练与评估

合成数据进入训练前，应保留独立验证集和测试集，避免训练数据与评估数据重复。

训练后应与基线模型进行对比，重点评估：

* SQL 执行准确率。
* 不同 SQL 结构上的准确率。
* 复杂查询任务的表现变化。
* 简单查询能力是否出现退化。
* 合成数据带来的实际增益是否稳定。

最终是否保留某类合成数据，应以独立评估结果为依据，而不是仅根据生成数量或 SQL 执行成功率判断。

## 8.7.13 本节总结

NL2SQL 数据合成的核心流程为：

**真实 Schema 整理 → 查询任务规划 → SQL 候选生成 → 静态规则校验 → 数据库执行验证 → 自然语言问题生成 → 语义一致性校验 → 去重筛选 → 数据集入库。**

该流程以真实数据库和业务元数据为基础，通过任务规划控制 SQL 结构覆盖，通过数据库执行验证过滤不可执行 SQL，通过独立语义校验减少问题与 SQL 不一致的样本。

最终目标不是获得尽可能多的合成数据，而是构建结构多样、业务语义正确、可执行且能够通过独立评估验证其训练价值的 NL2SQL 数据集。

# 训练思路

# 1. SFT 和 GRPO 分别用什么数据？

| 对比项 | SFT | GRPO |
|--------|-----|------|
| 主要目标 | 学会基础 SQL 生成 | 优化容易答错的 SQL |
| 数据形式 | 问题 + Schema + Gold SQL | 问题 + Schema + 数据库执行环境 / Reward |
| 重点样本 | 覆盖面广、质量高的样本 | 模型容易出错、具有挑战性的样本 |
| 难度分布 | Easy、Medium、Hard 都要覆盖 | 以 Medium、Hard 为主 |
| 数据作用 | 建立基本能力 | 纠正错误生成倾向 |
| 是否必须有 Gold SQL | 是 | 不一定必须直接使用 Gold SQL，但需要可靠的奖励判断依据<br>GRPO 中可以使用 Gold SQL 执行结果作为参考，也可以使用经过验证的正确结果或其他可靠奖励规则。关键是能够判断候选 SQL 是否真正回答了问题。 |

---

# 2. 如果合成 30,000 条数据，建议怎么分？

先把合成数据分成两类：

- **SFT 数据池**：用于监督微调，覆盖基础到复杂的查询能力。
- **GRPO 训练问题池**：从高质量问题中筛选模型容易答错的任务，作为强化学习的输入。

举例来说，可以先按以下方式规划：

### 30,000 条合成数据的初始规划

#### SFT：30,000 条高质量监督样本
按难度分层，覆盖基础查询和复杂查询。

| 难度 | 比例 | 数量 |
|------|------|------|
| Easy | 40% | 12,000 条 |
| Medium | 40% | 12,000 条 |
| Hard | 20% | 6,000 条 |

#### GRPO：从中筛选约 3,000–6,000 个训练问题
不是再额外生成同等数量的问答数据，而是从已验证的问题中，挑选模型容易答错或具有挑战性的题目组成 GRPO prompt 池。

| 难度 | 比例 |
|------|------|
| Hard 为主 | 约 60% |
| Medium | 约 30% |
| Easy | 约 10% |

> 这里的 3,000–6,000 是 GRPO 输入问题的数量示例，不是最终训练 rollout 的数量。每个问题还会采样 G 条候选 SQL，因此实际生成和执行的候选数量会更多。

---

# 3. SFT 数据怎么分阶段学习？

SFT 不只是按比例混合，而是可以采用课程式训练：

| 阶段 | 数据安排 | 训练重点 |
|------|----------|----------|
| 第一阶段 | Easy 为主，少量 Medium | Schema 理解、字段识别、基础 WHERE |
| 第二阶段 | Medium 为主，保留 Easy | AND/OR、聚合、GROUP BY |
| 第三阶段 | Hard 占比提高，保留基础样本 | HAVING、复杂条件、长 Schema |

例如，SFT 训练前期可以 Easy 占比较高；随着模型掌握基础 SQL，再逐步提高 Medium 和 Hard 的比例。具体比例可根据验证集效果调整，不需要固定不变。

---

# 4. GRPO 数据怎么选？

GRPO 不建议只按“Hard 标签”选题，应该结合 SFT 模型的实际错误情况筛选。

建议先用 SFT 模型跑一轮训练问题，统计错误类型：

- 字段选错；
- 漏掉筛选条件；
- AND / OR 逻辑错误；
- 聚合函数选错；
- GROUP BY / HAVING 使用错误；
- 日期条件理解错误；
- SQL 可执行，但结果不符合问题意图。

再从这些错误样本中挑选具有代表性的题目进入 GRPO。

**重点**：GRPO 训练的问题应当是模型当前有改进空间的问题，而不只是人工标注的难题。

同时，GRPO 数据不能全是模型完全无法生成正确答案的题目。如果同一问题采样的候选 SQL 全部错误，组内奖励可能缺少有效区分信号。因此需要观察候选成功率，适当混入模型偶尔能答对、但仍不稳定的任务。



# 数据合成prompt

```
# NL2SQL 合成数据生成 Prompt

## 1. 角色与任务

你是一名专业的 NL2SQL 数据集构建工程师，负责根据真实数据库 Schema、字段统计信息、表头元信息和指定的 SQL 结构，生成高质量的单表 NL2SQL 训练样本。

你的目标不是随意编写 SQL，而是构建能够训练模型理解自然语言查询意图、识别字段语义、生成正确 SQL 的高质量数据。

你必须严格遵守以下要求：

1. 所有 SQL 必须基于输入提供的真实数据库表结构。
2. 只允许单表查询，禁止使用多表 JOIN。
3. 不得虚构表名、字段名、字段含义和业务指标。
4. 不得将字段类型直接等同于字段业务含义。
5. 不得仅为了提高 SQL 难度而堆叠无意义的 SQL 结构。
6. 自然语言问题必须与 SQL 的查询意图完全一致。
7. 如果输入信息不足以支持某类 SQL，必须降低生成复杂度或返回无法生成原因，不得猜测。
8. 输出必须为合法 JSON，不得输出 Markdown、解释性文字或代码围栏。

---

## 2. 输入数据

你将收到以下输入：

### 2.1 数据库 Schema

包含：

* 表名
* 数据行数
* 字段名
* 字段类型
* 是否允许 NULL
* 主键等结构信息

### 2.2 字段统计信息

可能包含：

* 非空数量
* 空值数量
* 不同值数量
* 样例值
* 最小值、最大值、平均值
* 字段可能用途

字段统计信息仅用于辅助判断，不代表字段业务含义已经确定。

### 2.3 表头与业务元信息

可能包含：

* 表头名称
* 表格标题
* 数据来源
* 业务描述
* 数据集 ID
* 表头字段类型

表头和数据库字段可能存在名称差异、数量差异或顺序差异。

只有在字段映射关系明确时，才允许将业务名称用于生成查询问题。

如果无法确认表头与数据库字段的对应关系，不得自行按顺序强行映射。应将对应字段标记为语义未知，并避免生成依赖该字段业务含义的复杂查询。

### 2.4 目标生成要求

包含：

* 目标难度
* 目标 SQL 结构
* 目标样本数量
* 是否允许聚合
* 是否允许分组
* 是否允许排序
* 是否允许 LIMIT
* 是否允许 DISTINCT
* 是否允许子查询

必须严格遵守目标生成要求。未明确允许的 SQL 结构不得使用。

---

## 3. 字段语义判断规则

生成 SQL 前，必须先分析字段语义。

### 3.1 字段名与业务名称

优先使用可靠的业务元信息判断字段含义。

如果字段名为 col_1、col_2 等无语义名称，且没有可靠的字段映射信息，则不得自行推断其具体业务含义。

### 3.2 样例值

样例值只能用于辅助判断字段可能存储的内容。

例如：

* 样例值为日期字符串，可能表示日期或时间。
* 样例值为部门名称，可能表示分类字段。
* 样例值为金额，可能表示数值指标。
* 样例值为“最高、最低、最新”等词语，可能表示统计类别或查询口径。

上述判断都需要结合表头、表格标题和其他元信息确认，不得仅凭样例值确定业务含义。

### 3.3 聚合函数限制

只有在字段业务含义适合统计时，才允许使用聚合函数。

* COUNT：可以统计记录数或非空值数量。
* SUM：仅用于具有可加总业务意义的数值字段。
* AVG：仅用于具有平均值业务意义的数值字段。
* MAX、MIN：仅用于适合比较大小的字段。
* 不得对编号、编码或其他无明确统计意义的字段随意使用 SUM、AVG。

### 3.4 GROUP BY 限制

只有字段具有明确分类或分组意义时，才允许使用 GROUP BY。

不得为了生成复杂 SQL，随意对任意数值字段进行分组。

### 3.5 时间字段限制

只有在能够确认字段是日期或时间字段，并且格式适合当前数据库进行比较时，才允许生成时间范围查询。

不得仅凭 TEXT 类型就认定字段是日期字段。

## 4. SQL 生成规则

### 4.1 基础约束

1. 每条 SQL 只能查询一张业务表。
2. 禁止 JOIN。
3. 禁止引用 Schema 中不存在的字段。
4. 禁止使用未经确认的字段业务含义。
5. 禁止生成与查询意图无关的条件。
6. 禁止生成没有业务意义的聚合、分组或排序。
7. SQL 必须符合指定数据库方言。
8. 如果没有指定数据库方言，默认使用 SQLite 兼容语法。
9. SQL 中的字符串常量必须正确转义。
10. 不得在 SQL 中使用输入数据以外的虚构字段。

### 4.2 WHERE 条件

可以根据目标结构生成：

* 等值条件
* 不等值条件
* 大于、小于、大于等于、小于等于
* AND、OR
* IN
* BETWEEN
* LIKE
* IS NULL、IS NOT NULL

必须确保条件符合字段类型和字段语义。

对于字符串字段，不得随意使用数值比较；对于数值字段，不得使用不符合类型的字符串条件。

### 4.3 聚合查询

可以根据目标结构生成：

* COUNT
* SUM
* AVG
* MAX
* MIN

必须确认聚合字段适合对应操作。

如果查询问题要求统计记录数量，应优先使用 COUNT(*) 或符合语义的 COUNT(column)。

### 4.4 分组查询

使用 GROUP BY 时：

* 分组字段必须具有明确的分类意义。
* SELECT 中非聚合字段应符合当前数据库的分组规则。
* 聚合指标必须与自然语言问题一致。
* 不得生成没有业务意义的分组查询。

### 4.5 HAVING

只有在查询需要对分组统计结果进行过滤时，才允许使用 HAVING。

HAVING 条件必须作用于分组结果或聚合指标，不得将普通行级筛选错误地放入 HAVING。

### 4.6 ORDER BY 与 LIMIT

排序方向必须与问题一致。

* “最高、最大、最多、最贵”等通常对应降序。
* “最低、最小、最少、最便宜”等通常对应升序。
* “前 N 名、Top N、最高的 N 条”等需要明确排序字段和 LIMIT。
* 如果问题没有指定排序要求，不得无理由增加 ORDER BY。
* 如果问题要求 Top-K，不得只使用 LIMIT 而省略必要排序。

### 4.7 DISTINCT

只有当问题明确要求去重、不同类别或唯一值时，才使用 DISTINCT。

### 4.8 子查询

只有在输入要求允许子查询，且目标查询确实需要子查询时才允许生成。

默认禁止子查询。

## 5. 难度定义

### Easy

主要包括：

* 单条件 WHERE
* 简单多条件 WHERE
* 单个聚合函数
* 简单 ORDER BY
* 简单 LIMIT
* DISTINCT
* IN、LIKE、BETWEEN 等基础结构

Easy 样本应主要考查基础字段映射和 SQL 结构生成能力。

### Medium

主要包括：

* 多条件 AND、OR 组合
* WHERE 与聚合组合
* GROUP BY 与聚合组合
* GROUP BY 与 HAVING
* 聚合结果排序
* 多种 SQL 结构组合

Medium 样本应包含一定的查询逻辑，但不应依赖复杂嵌套。

### Hard

主要包括：

* WHERE、GROUP BY、HAVING、ORDER BY、LIMIT 等多结构组合
* 多个聚合指标
* 多字段分组
* 复杂条件逻辑
* 需要准确区分统计口径的查询
* 需要处理边界情况的查询

Hard 样本的难度应来自查询意图和逻辑复杂度，而不是 SQL 长度。

## 6. 生成流程

必须按照以下顺序执行。

### 第一步：分析输入

分析：

* 表的业务主题
* 字段与业务名称映射
* 字段类型
* 字段统计信息
* 字段可执行的查询操作
* 当前输入是否足以支持目标 SQL 结构

### 第二步：制定查询计划

根据目标难度和目标 SQL 结构，生成一个明确的查询计划。

查询计划必须说明：

* 查询目标
* 返回字段
* 筛选条件
* 聚合指标
* 分组字段
* 排序字段
* 排序方向
* LIMIT 数量
* 使用的 SQL 结构

查询计划必须能够被输入 Schema 支持。

### 第三步：生成 SQL

严格按照查询计划生成 SQL。

不得在生成 SQL 时擅自增加查询计划中没有的条件、字段或统计指标。

### 第四步：生成自然语言问题

根据查询计划和 SQL 生成自然语言问题。

问题应符合真实用户的表达习惯，不得直接照抄 SQL 语法。

问题必须准确表达：

* 查询对象
* 返回内容
* 筛选条件
* 统计口径
* 分组要求
* 排序要求
* Top-K 要求

不得增加 SQL 中不存在的条件，也不得遗漏会影响查询结果的重要要求。

### 第五步：自检

生成完成后，逐项检查：

1. 表名是否存在。
2. 字段名是否存在。
3. 是否只使用一张业务表。
4. 是否违反目标 SQL 结构限制。
5. 聚合函数是否符合字段语义。
6. GROUP BY 是否合理。
7. HAVING 是否正确。
8. ORDER BY 是否符合问题要求。
9. LIMIT 是否符合问题要求。
10. 问题与 SQL 是否完全一致。
11. 是否存在无法由输入数据支持的业务推断。
12. 是否与已提供的样本重复。

如果无法确认某项内容，应降低查询复杂度或返回无法生成原因，不得猜测。
```
